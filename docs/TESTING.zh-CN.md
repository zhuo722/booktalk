# 测试

[English](TESTING.md) · **中文**

三层测试，每一层都便宜到可以在每次改动后都跑一遍；此外还有一次要花钱的测量，以及一份需要人拿着麦克风走一遍的清单。

| 层 | 是什么 | 代价 |
|---|---|---|
| **369 个离线测试** | 针对 `FakeAIClient` 的 `pytest`；不联网、不需要 key、不碰真实数据目录 | ~秒级 |
| **11 个前端单测 + `tsc`** | vitest 覆盖 SSE 解析器、音频队列和请求超时期限；一次零报错的 TypeScript 构建 | ~秒级 |
| **评测脚手架** | 在测试用书上跑六个消融实验分组，`--fake` 离线或用真实 key | fake 约 6 s，真实约几分钟 + API 花费 |
| **手工端到端** | 测试框架抓不住的东西：麦克风、Safari、锁屏 | ~10 分钟 |

前三层是快速循环。第四层用来发现测试框架看不见的缺陷：两个已经发布出去的后端 bug，以及交互 UI 阶段的大部分问题——它们是靠实际运行程序发现的，而不是靠测试——见 [AI_WORKFLOW.zh-CN.md](AI_WORKFLOW.zh-CN.md)。

## 靠什么做到：一个接缝和一个假实现

应用里每一次模型调用都经过 `AIClient` Protocol（`app/services/openai_client.py`）。`FakeAIClient` 以确定性的方式实现了它：

- **Embedding** 由 `sha1(text)` → `numpy.RandomState` → 单位归一化向量生成。相同文本永远得到相同向量，因此检索可复现。**相似文本得到的向量彼此无关**——向量检索的相似度在构造上就是噪声，测试只能依赖"文本完全相同则结果相同"这一点，绝不能依赖语义上的接近。这是刻意加的限制：一个连语义也一并伪造的假实现，会让坏掉的流水线也通过测试。
- **Chat** 按调用点给出预置回复。调用方用 `purpose="rewrite" | "rerank" | "answer" | "toc_levels" | "context" | "summary"` 标记每次补全，假实现为每一种返回*形状*正确的回复——`toc_levels` 得到严格 JSON 的层级列表，`context` 得到一句定位用的说明，`rerank` 得到有序的下标列表。正是这一点让入库过程中的 LLM 层级可以在离线状态下被真正跑到，而不是被跳过。
- **TTS** 返回合成的 PCM，长度是句子的函数，因此 `seq` 顺序、"字节数即时长"这一不变量以及 `AudioPacer` 的背压算术，都可以在没有真实音频的情况下测试。
- **转写**返回一个固定字符串，并记录传给它的 `prompt`，ASR 词表偏置的测试就是靠这一点断言提示确实被发了出去。

假实现还会记录每一次调用（`embed_calls`、`chat_calls`、`tts_calls`、`transcribe_prompts`），所以测试断言的是*向模型提出了什么请求*，而不只是返回的答案。

**合成 PDF** 在测试内用 PyMuPDF 按真实坐标生成——带字号的字体、页边距、书眉和页码——所以结构识别、重复行检测器和页码映射面对的是真实的版面几何，而不是一个 mock。

## 前端

```bash
npm run test     # vitest, node environment
npm run build    # tsc -b && vite build — zero TypeScript errors is the bar
```

十一个单测覆盖客户端的三块逻辑，它们都是输入的纯函数，出错时不会发出任何声响：

- **基于 POST 的 SSE 读取器**——事件被切在中间的 chunk 边界、多行 `data:`、abort 行为；
- **音频队列**——base64 → int16 → float32 的转换，以及按 `seq` 排序的调度：乱序到达的分段要等待，而不是重排；
- **请求超时期限**——一个永远不返回的 fetch 必须变成 UI 能显示出来的错误。这一条存在是因为故障真的发生过：后端停掉之后，开发服务器的代理接受了连接却从不应答，于是麦克风按钮停在忙碌状态，启动时的健康探测也永远不结束，连带把那个本该说明原因的提示条一起拖住了。这些测试在假定时器下挂住一个 fetch，断言普通调用在 15 s 放弃、转写还在继续等并在 60 s 放弃、连不上的服务器和慢服务器读起来不一样，以及已经开始的回答流在远远超过 20 s 的响应头期限之后仍然继续运行。

客户端剩下的部分是 DOM 和音频硬件，那正是手工清单要覆盖的。

`mock/server.mjs` 这个后端也是一个测试面：它用预置数据实现了完整的 API 契约，所以整个 UI——书架、入库进度、飞入阅读页的过渡、流式回答、PCM 播放、取消——都可以用 `npm run mock` 在没有 key 的情况下跑起来。它需要被有意识地维持与真实后端一致，因为它跑偏时不会有任何东西失败：它的章节带着 `opening` 正文，它的来源带着完整的段落（`text`，其中 `preview` 是前 200 个字符，切法与服务端完全一致），阅读页的章节页和 "Full passage" 控件正是靠这些才在离线状态下真的能用，而不是悄无声息地失效。

## 评测脚手架

它不是测试，是一次测量。它回答的是"这套检索是不是真的比朴素分块更好，以及是哪一部分在起作用？"测试用书、问题集、各分组和指标的完整说明见 [`backend/eval/README.zh-CN.md`](../backend/eval/README.zh-CN.md)。结果见 [`backend/eval/report.md`](../backend/eval/report.md)。

```bash
cd backend
.venv/bin/python eval/make_fixture_book.py     # ~2 s — writes fixture PDF + golden.json
.venv/bin/python eval/run_eval.py --fake       # ~6 s, offline, no key
.venv/bin/python eval/run_eval.py --fake --sweep

.venv/bin/python eval/run_eval.py              # all six arms, real models
.venv/bin/python eval/run_eval.py --arms A,F   # just the two endpoints
.venv/bin/python eval/run_eval.py --sweep-only --no-answers
```

常用参数：`--limit N`（每个类别 N 个问题）、`--no-answers`（只算检索指标——省掉大约四分之三的花费）、`--reuse`（保留上一次运行留在 `eval/.work` 里的索引）、`--data-dir`、`--report`、`--results`。

一次真实运行会在一本 25 页的书上建四套索引，对六个分组各问 88 个问题：大约 500 次 chat 补全和 800 次 embedding 调用，另外 F 组的索引还要为每个 chunk 做一次上下文增强调用。key 在运行时从环境变量或 `backend/.env` 读取，从不打印。

**`--fake` 能证明什么、不能证明什么。** `FakeAIClient` 的 embedding 在构造上就是噪声，所以只用向量检索的分组得分接近零，比它们高出来的部分都是 BM25 撑起来的；预置的 chat 回复意味着所有回答类指标衡量的都是这个假实现；D 组的 cross-encoder 被换成一个确定性的词面替代实现，所以不会下载任何模型。`--fake` 全绿只能证明脚手架、四套索引配置、六套检索配置、ASR 修复路径和报告生成器都能端到端跑完。**值得引用的数字来自使用真实 key 的运行**，而 `report.md` 会在自己的头部写明它是哪一种运行产出的。

`make_fixture_book.py` 不会写出一份它无法担保的测试用书：在输出任何东西之前，它会检查每个期望答案的子串确实印在书里、每句证据都能原样通过 PDF 抽取、生成的 PDF 经过应用*自己*的结构识别重新解析后得到十二个名字正确的章节，以及全部十二处 ASR 错误都能对着 `app.ingest.vocab` 从同一段正文里抽出的词表修复回来。`run_eval.py` 在加载时会重新校验 `golden.json`，所以手工改过的标准答案集不会悄悄产出没有意义的数字。

## 手工端到端清单

离线测试拿不了麦克风，而两个真正发布出去的线上 bug 都是用真实 key 跑真实程序时发现的。UI 阶段的那些交互故障也一样——一个把自己的目标位置量错了的过渡、一个在好答案上也会触发的警告、一个转写正确却把结果悄悄丢掉的麦克风——它们没有一个会被本仓库里的任何断言抓到。在宣布一次改动完成之前，把这份清单走一遍。

最后那一个值得完整讲一遍，因为这正是这份清单存在的理由。输入区保存了一个 `alive` ref，好让在用户已经离开阅读页之后才返回的转写结果，不会在没人看的界面上发起提问。清理函数把它置为 `false`；没有任何地方把它置回 `true`。React 的 StrictMode 在开发环境下会把每个组件挂载、卸载、再挂载一次，所以这个标志从第一次渲染起就是 false：`/api/asr` 返回 200，提前 return 丢掉了转写结果，而同样以这个标志为条件的 `finally` 分支也从没把麦克风从忙碌状态里放出来。每一层都报告成功。是服务端日志点出了问题：`POST /api/asr 200 OK` 后面没有跟着 `POST /api/chat`，一次又一次。**当某一步自己的日志全都说"没问题"时，去看下一步始终没有收到什么。**

**准备：** `backend/.env` 里放真实的 `OPENAI_API_KEY`，后端跑在 `:8000`，`npm run dev` 跑在 `:5173`，Chrome 和 Safari 都开着。

1. **没有 key 的冷启动。** 把 `.env` 挪走再启动。应用能提供服务，`/api/health` 报告 `openai_configured: false`，UI 能加载，上传失败时给出的是配置说明而不是堆栈。全程不应该发出任何网络调用——没有 key 时重排模型的预热绝不能触发。
2. **麦克风权限——授予。** 在一个全新的浏览器配置里点麦克风。浏览器的权限提示出现，按钮变成由真实输入音量驱动的动态圆环，停止后进入 "Transcribing…"，再进入流式回答。盯住按钮是否回到空闲状态、问题是否出现在对话里——一条到达后被丢掉的转写，看起来和从没到达过一模一样，而 `npm run dev` 跑在 StrictMode 下，生产环境不是。
3. **麦克风权限——拒绝。** 拒绝之后再点一次。UI 必须说明如何在浏览器里重新开启它，而不是无声失败或者一直转圈。
4. **首次出声。** 问一个事实性问题，然后*听*。文字还在流式输出时声音就应该开始了——在网络面板里把 `done` 事件的 `first_audio_ms` 和你实际听到的时间对照一下。句子之间不能有空隙，顺序不能乱；出现咔哒声或者重复，就是 `seq` 调度的 bug。
5. **停止按钮。** 在回答中途打断。声音立刻停止，流被中止，屏幕上看到的回答被截断到实际念出来的部分。然后追问一句（"那它的港口呢？"）——它必须基于*被截断的*那份文字来理解，这正是 `played_seq` 的全部意义。
6. **Safari。** 在这里 MediaRecorder 产出的是 `audio/mp4` 而不是 webm，并且 AudioContext 必须在点击手势内部创建，否则什么都放不出来。录音、转写、听一遍。如果手边有设备，再在 iOS Safari 上重复一次。
7. **一本真实的大书。** 上传一本 300 页以上的。观察阶段序列和进度条是否单调前进；确认解析过程中内存保持平稳；确认 TOC 与书里印刷的目录一致；就靠后的某一章提问，然后打开 PDF 核对引用的页码是不是真的对。
8. **一本扫描版的书。** 上传一份纯图片的 PDF。它必须被拒绝并给出每页字符数的提示，而不是被接受然后悄悄建成一个空索引。
9. **锁屏 / 后台行为。** 开始一次回答，然后锁屏或者切到别的标签页。WebAudio 会被浏览器挂起；回来之后，播放不能与文字失去同步，也不能把积压的旧音频一口气放出来。如果出现了，修复要做在客户端——服务端早已把那些分段发完了。
10. **一本中文书。** 上传一本并用中文提问。结构识别应当找到 `第N章` 这样的标题，BM25 应当走 jieba 分词，回答应当用提问所用的语言返回。注意 ASR 词表/修复这条路径按设计只支持英文，在这里什么也不做。
11. **两个浏览器，同一本书。** 同时从两边提问。会话以 `(session_id, book_id)` 为键，两边的历史不能互相串。
12. **引用依据警告。** 问一个书里答得很好的问题：句子会带上各自的边注，**不出现横幅**。问一个书里从没提过的主题：回答是一句简短的拒答，它按设计不带任何引用，并且因为 >80 字符的判断而被排除在警告之外。想看到横幅本身，就问一个啰嗦的问题，让模型能靠自己的知识作答而检索到的段落并不支持它。绝不能出现的是：一个引用充分的回答上面挂着横幅。这个警告统计的是回答自己的句子里有多少条被事后的引用归属追溯回了某个段落——**不是**检索置信度，后者在一本真实的书上两个方向都测错过："第二章讲了什么"得到 0.0017，而这个问题是靠四段被引用的原文正确回答的；一个书里从没提到的主题得到 0.9953。那个分数仍然会被计算，仍然随 `sources` 事件发出；只是它不再决定读者看到的任何东西。
13. **打开一条来源。** 展开回答下面的来源列表，点某张卡片上的 "Ch. N · pp. x–y" 引用。对话旁边的书必须翻到**那一段**——它所在的章、它的页码、它自己的文字，并以被引用句子所带的颜色标出——而不只是翻到它所属的那一章。然后点 "Full passage"：显示的内容必须比卡片上已经印出来的更多（卡片放的是 200 字符的预览，来源里带着整个 chunk）。用章节条翻走之后，页面回到该章开头的正文。
14. **书架 → 阅读页 → 书架。** 在书架上点一本书。它在原地变成方形并抬起，然后同一个封面飞到阅读页，落定之后页面才展开。只有封面应该跨屏移动：字标停在原处不动，两边界面的其余部分围绕它完成交接。返回时是抵达过程的镜像，方向朝右。留意这个过渡真实出现过的问题——封面在交接的瞬间跳成另一种形状或尺寸、书还在飞的时候页面就画在了对话上面、以及飞行量不出来时阅读页停在半路（目标位置量不出来也必须把页面打开）。然后打开减弱动效再走一遍。
15. **回到离开时的位置。** 把书架往下滚很远，从底部打开一本书，然后返回。书架必须回到离开时的滚动位置，书落回它自己那一行——而不是回到顶部，让飞行动画指向一个谁也看不见的行。
