# AI 工作流

[English](AI_WORKFLOW.md) · **中文**

BookTalk 实际是怎么做出来的。这是一份过程记录，不是方法论推销——流程失效的地方同样写
了下来，因为一个只汇报成功的工作流不能证明任何事情。

第一手材料是那些产出物，它们都在这个仓库里：写在代码之前的 [SPEC.md](../SPEC.md)、背后
带着 agent 原始输出的 [RESEARCH.md](RESEARCH.zh-CN.md)、测试套件，以及评测的逐题 CSV。
历史以单个提交交付，所以工作的顺序由这份文件本身承载，而不是靠指向某个提交。

真正的构建过程分十步：

```
 1  技术规格，写在任何应用代码之前
 2  三个开源设计 skill，通读之后采纳为有约束力的依据
 3  五个 agent 的并行调研，收进规格作为 §14
 4  后端 v1，按规格实现
 5  前端 v1，按同一份规格实现，与后端并行且不需要协调
 6  按新的视觉方向重建前端
 7  后端 v2：结构阶梯、FlashRank、引用、PCM 语音、评测工具
 8  启动时迁移的顺序问题——一个只有真实运行才能发现的 bug
 9  给 OpenAI SDK 显式传 base_url——同类的第二个 bug
10  真实的六组消融实验，测试用书、标准答案集和结果一并提交
```

之后还有 5 个较小的轮次，遵循同样的模式——章节梗概、引用传输格式的修复、文档、一次三视角
对抗式评审及其修复，以及一处测试数量订正——在 §5 中说明。再往后是完全另一类工作，有自己
的章节：交互阶段（§7）和最终审计（§8）。

从上往下读，这个顺序说出了值得说的那件事：**先写规格，再做调研，然后实现，接着是两个只
有真实运行才能发现的 bug，最后是测量。** 没有任何东西在被规定之前就动手实现，也没有任何
结论在被测量之前就写出来。

---

## 1. 规格先行，而且规格有约束力

[SPEC.md](../SPEC.zh-CN.md) 写在任何一行应用代码之前，而且它是一份合同，
不是草图：文件树、模块职责、SQLite DDL、`AIClient` Protocol 签名、SSE 事件序列、token
预算，以及逐阶段的完成定义。它自己的开头第一句就写着：实现 agent 必须严格照做，规格没有
规定的地方优先选最简单的方案。

起支撑作用的决定是**提前把 API 契约（§6）和 SSE 事件结构（§5.2）钉死**。正是它让后端和
前端可以并行开发、两边之间零协调：前端 agent 从来不需要问后端 agent 任何问题，因为这些
问题已经用文字回答过了。`frontend/mock/server.mjs` 存在也是同一个原因——它用预置数据
实现了 §6，所以在它对接的后端还不存在时，UI 就已经能完整跑起来了。

这个做法的代价同样看得见。v2 调研（SPEC §14）推翻了原设计中足够多的部分，以至于真实的
模块树已经和 SPEC §3 画的那棵树对不上了：`ingest/` 多了 `toc.py`、`headings.py`、
`markdown.py`、`vocab.py`、`enrich.py`、`prompts.py`；`speech/` 多了 `pcm.py`、
`turns.py`、`phonetics.py`；`rag/` 多了 `citations.py`。TTS 从 mp3 改成了裸 PCM，引用从
行内标记改成了事后归属。
与其把那一节改写成一句关于"当时到底计划了什么"的谎话，SPEC §14 直接写明每条修订覆盖了
哪一节，而那棵树作为历史记录留在原地。

到了交互阶段（下面的 §7），这个偏差又扩大了一次：SPEC §7 画的那套前端——`Shell`、
`Library`、`Toc`、`BookCard`、一条 300px 的左侧栏——已经不存在了，而 `Shelf`、`Reader`
以及两者之间的飞行动画在规格里根本找不到，因为写规格的时候没人想到它们。处理方式相同：
SPEC §3 和 SPEC §7 现在开头都有一段说明，指出交付的代码丢下了哪些部分，以及当前形态写在
哪里（[ARCHITECTURE.md](ARCHITECTURE.zh-CN.md)、[DESIGN.md](../frontend/DESIGN.zh-CN.md)、
[DESIGN-SHELF.md](../frontend/DESIGN-SHELF.zh-CN.md)）。一份被悄悄改成和代码一致的规格，
就不再能证明任何事情。

## 2. 规划与执行的角色分工

两档模型，做不同的事：

- **规划模型**（Claude Fable 5）写了 SPEC.md、设计说明和 agent 契约，并且只在每个阶段
  边界评审，而不是持续评审。第 6 步的前端重建也是它自己做的，因为那里的瓶颈是
  视觉判断而不是产出量。
- **执行 agent**（Claude Opus 5）按这些契约做实现——后端 v1、前端 v1、v2 升级、集成测试
  套件、评测框架。

这个分工是有意的：写契约和满足契约是两种不同的能力，而一个自己写验收标准的 agent 永远
都能达标。按阶段边界评审而不是按文件评审，让评审者盯的是这个*阶段*有没有达到它的目的，
这和每个 diff 在局部是否合理是两个问题。

## 3. 外部输入：审过再用，而不是直接信

两条渠道，都在仓库里留下了产物。

**从 GitHub 采纳的设计 skill。** 三个开源 skill 包被完整读过，然后才采纳：来自
[Leonxlnx/taste-skill](https://github.com/Leonxlnx/taste-skill)（MIT）的 `minimalist-ui`
和 `redesign-existing-projects`，以及来自 [pbakaus/impeccable](https://github.com/pbakaus/impeccable)
（Apache-2.0）的 `impeccable-craft`。来源、许可证和确切改动记录在
[`.claude/skills/README.md`](../.claude/skills/README.md)，并且只安装了指令文件——没有
脚本、没有 hook、没有任何来自我们无法控制的仓库的可执行内容。随后 SPEC §7 被修订，把这些
skill 定为前端质量上的*最终依据*，在冲突时覆盖规格自己的 token 选择（规格原本的正文字体
Inter 就是被这条规则划掉的）。采纳外部审美，然后让它推翻自己更早的决定，这一步才让采纳
是真的，而不是装饰。

**五个 agent 的调研。** 在设计定稿之前，五个 agent 并行跑了一轮——RAG 产品、PDF 解析、
语音管线、检索与评测、前端——指令要求它们**读真实源码并验证结论**，而不是凭记忆作答。
大约 500k token，309 次工具调用，墙钟时间约 16 分钟；完整输出保存在
[`docs/research/raw-recommendations.txt`](research/raw-recommendations.txt)，综述在
[`docs/RESEARCH.md`](RESEARCH.zh-CN.md)。

让它不只是一篇文献综述的，是每条建议在采纳前都*在这台机器上跑过基准*：FlashRank 的模型
实测 5 MB，20 个段落约 7.6 ms，且 cp39 wheel 能正常解析安装；pymupdf4llm 在一本真实的
244 页书上和裸 `get_text()` 做了对比（129 个合字字符和 68 处行末连字符断行 → 0 和 0）；
Docling 的 `HybridChunker` 是读源码看的，`semchunk` 验证过能在 Python 3.9 上安装。
GitHub 上的数据是当场查的而不是假设的——结果发现 Verba 已归档，chatbot-ui 和 vocode
大约两年没更新——并且**明确不把流行度当作适配度**。

活下来的建议变成了 SPEC §14，这也是调研那一步改的是规格而不是代码的原因。被否掉的也
连同理由一起写下来了——LangChain、ragas/deepeval、HyDE、late chunking、完整的 RAPTOR、
把语义分块作为主路径、Tailwind/shadcn、浏览器端 VAD、wavesurfer.js——因为一个设计同时也
是它决定不做的那些事，而一个没写下来的否决和一次疏漏无法区分。

## 4. 结构化的责任落实：一个必填的 deviations 字段

每个 agent 都要返回一份机器校验的结构化报告，schema 里包含一个**必填的 `deviations`
数组**。不是可选的，也不是写在末尾的自由文本：是一个不填就通不过校验的字段。

它之所以存在，是因为一个能力强的 agent 最典型的失败模式，是给出一份自信的总结，同时悄悄
略过它做得和要求不一样的那三个地方。把偏离做成一等输出改变了激励——报告偏离是合规，隐瞒
偏离是 schema 违规。

上报的偏离随后会被**评审，而不是走过场盖章**。有些被接受并写回规格（上面 v2 的模块树很
大程度上就是被接受的偏离）。有些被驳回退回重做。这个区分之所以存在，只是因为那个字段逼着
这场对话必须发生。

## 5. 验证文化，以及照样漏过去的那些 bug

规则是：每个 agent 自己验证自己的产出，编排者再独立复验一遍。agent 跑它们自己的测试；
编排者再跑一遍，读 diff，并且拿产物而不是拿总结去核对结论。

**这还不够。** 下面两个都通过了当时套件里的 363 个绿色测试（今天是 375 个）和一次独立
复验，然后在拿真实 API key 端到端跑应用的几分钟之内就被发现了：

- **启动时迁移的顺序。** `init_db` 在一次有序的遍历里同时创建表、索引和列
  迁移，于是 `CREATE INDEX idx_chunks_kind` 跑在了 `ALTER TABLE chunks ADD COLUMN kind`
  *之前*。所有测试都看不见它，因为每个测试都从一个全新的临时数据库开始，那里这个列本来
  就在 `CREATE TABLE` 里。它只咬在 v2 schema **之前**创建的数据库上——也就是恰好整周都
  在跑 v1 的那台开发机。修复方式是把这一遍拆成 表 → 迁移 → 索引，并由
  `tests/unit/test_db_migration.py` 钉住：它构造一个 v1 形态的 `chunks` 表，然后断言列
  和索引事后都存在。
- **一个空的 `OPENAI_BASE_URL` 污染了 SDK。** `.env.example` 里带着
  `OPENAI_BASE_URL=`，作为一个有文档说明的空覆盖项。dotenv 把它加载成 `""`，应用传的是
  `base_url=None`，于是 OpenAI SDK 回退到自己去读环境变量——在那里读到了空字符串，拼出
  了错误的请求 URL。让它*难查*而不是一眼可见的，是代码里到处都是出于好意的逐 chunk
  回退：上下文增强调用失败就降级为静态面包屑，TTS 调用失败就把一句话降级成纯文本，重排
  模型失败就降级为融合顺序。它们每一个都尽职地工作了，所以应用继续能用，只是悄悄少做了
  一些事。修复方式是在 `config.py` 里把空值归一为 `None`，并且**始终**向 SDK 显式传入
  `base_url`。

关于第二个，有两点如实说明。第一点是它靠什么守住的——这一段本身就值得当作它所讲主题的
一个例子来读。它的初稿写的是：这个修复由一条代码不变量和调用点的一条注释守住，**没有
属于它自己的回归测试**，因为这个故障只有对着真实 SDK 才能复现。这句话在写下来的时候就
已经是错的：现在 `tests/unit/test_client_params.py` 里的那两个测试——环境里一个空的
`OPENAI_BASE_URL=` 绝不会传到 SDK，以及配置过的值会被使用——早在上一轮
就落地了。如实的说法比这两种讲法都更窄：那两个测试断言的是构造出来的 client 的 base URL，
所以它们钉住的是这个 bug 跨过的那道边界，而不是它造成的那些错误请求。这个说法是照着记忆
中的代码状态写的，而不是照着仓库里实际的样子写的，而且没有任何东西核对过它——正是 §4
为了在实现 agent 身上抓住而存在的那种失败模式，这次出现在了文档里。
第二点，一般性的教训是让人不舒服的那条：*优雅降级会把 bug 从测试面前藏起来*。这个代码库
里的每一处回退单独看都站得住，合在一起却让一次彻底的配置错误看起来只是状态差了一点的
一天。

**同一类的第三个，是在准备演示时发现的，也是这份文件里最清楚的一个例子。** 按住麦克风什么
都不会发生：没有回答，没有报错，按钮一直转。输入区维护着一个 `alive` ref，用来保证一次在
用户已经离开阅读页之后才返回的转写，不会把问题问到一个没人在看的界面上。清理函数把它置为
`false`，却没有任何东西把它置回 `true`。React 的 StrictMode 在开发模式下会把每个组件挂载、
卸载、再挂载一次，于是这个标志从第一次渲染起就是 `false`：`/api/asr` 返回 200，提前返回把
转写丢掉，而 `finally` 里那句——同样受这个标志控制——也就永远没让麦克风退出忙碌态。每一层
都报告成功。点破它的是服务端日志：`POST /api/asr 200 OK`，后面没有任何 `POST /api/chat`，
一次又一次。**当每一步自己的日志都说"正常"时，去看下一步始终没收到什么。** 同一次运行还
暴露出：后端停掉时界面会一直停在加载态而不是报错，因为没有任何请求带截止时间。两个修复都
有测试，[TESTING.md](TESTING.zh-CN.md) 里的手工清单也改成了要盯着问题真的出现在对话里，
而不只是盯着转写开始。

另有三个 bug 被更早地抓住，根本没进到最终代码里，抓住它们的是集成测试 agent——它拿到的要求是
**攻击**这条管线，而不是确认它。契约里的对抗性设定找出了一些缺陷；同一个 agent 如果拿到
的要求是"写集成测试"，它会绕开这些缺陷写出能通过的测试。

**第三个缺口，是在写这份文档的时候发现的。** 后端按 SPEC §14.7 把引用映射发成
`{"map": [{"sentence_idx", "chunk_ids"}]}`；客户端读的是 `payload.citations`，形状是
`{sentence, chunk_id}`，也就是 `mock/server.mjs` 发的那种。于是逐句边注对着 mock 渲染得
完美无缺，对着真后端则静默地什么都不渲染——又因为客户端的兜底是没有标注的纯文本，看上去
也不像坏了。它能活过 363 个测试，结构性原因和上面两个 bug 一样：**mock 是前端的判定
基准，而它和它所校验的客户端出自对规格的同一次阅读。** 一份契约需要一个实现和一个*独立
推导出来的*消费方，而不是同一个作者的两次阅读。文档那一轮只上报了它而没有修（那一轮的
范围是文档）；随后编排者把客户端改成读服务端的 `{"map": [{sentence_idx, chunk_ids}]}`
形状，并把 mock 订正成对齐真实的传输契约——现在 mock 抄的是服务端，不再抄客户端。

**然后它又漂移了一次，方式和上一段预言的一模一样。** 交互阶段（§7）给后端加了两样新东西
——TOC 的章节要带上它的 `opening` 正文，来源要以 `text` 完整携带原文段落而不是只给
200 字符的 `preview`——因为阅读页和它的 "Full passage" 控件需要这两样。mock 两样都没跟着
更新，于是这两个功能在离线演示路径上是死的，对着真服务端却一切正常：章节页回退到了生成的
梗概，"Full passage" 打开的是它本来就已经在显示的 preview。没有任何东西报错，因为没有
任何东西检查 mock 是否仍然实现了它声称实现的那份契约。这是同一个结构性缺陷的*第二*次
出现，而上一段里的那个修复——让 mock 抄服务端——根本不可能防住它。只有"如果重来，我会
怎么做"里的那份共享 fixture 才能防住。

## 6. prompt 使用效率

模式是**每个 agent 一份详尽的契约**，而不是反复纠偏。每个实现 agent 拿到的说明里已经
包含了它必须满足的接口、必须使用的常量、完成的定义，以及它必须返回的报告 schema——所以
昂贵的来回只发生一次，以文字的形式，发生在为生成代码花掉任何 token 之前。写规格比事后
纠正便宜，而且它会留下产物。

在所有由契约驱动的阶段里——一直到文档那一轮为止——**向运行中的 agent 发消息更新范围
恰好只发生过一次**。这个数字是有意设的指标：每多一条中途消息，都是契约当初写得不够细的
证据，而把契约写到足以避免这类消息的自律，和产出 SPEC.md 的是同一种自律。它同时也是一个
只有在存在可对照契约时才有意义的指标；§7 就是那个没有契约的阶段，它不报这个数。

## 7. 交互阶段：17 轮没有对照物可查的工作

四个小时，17 轮，§1–§6 里的那套装置几乎全都不适用。没有契约可以满足，因为验收标准是一个
人在屏幕上看到了什么，而这件事没法提前写得精确到可以核对。循环是：跑起来，看着它，量出
哪里不对，修那一件事。一件一轮。

**做了什么。** 撤掉早期设计里的深色侧栏，把应用重做成一个统一的浅色界面，蓝色是唯一的强
调色，珊瑚色留给录音，并校验了 44 组对比度配对。对话之前放了一个书架：一行一本书、通栏
排布，每本是一个平躺的 CSS-3D 立体书，配一条带滚动联动高亮的固定刻度轨。接着让阅读页*就
是*那本书，而不是书旁边的一块面板——这一步删掉了 `Shell`、`Library`、`Toc` 和 `BookCard`，
以及因它们被删而失去引用的 65 个 CSS 块。紧接着的下一轮又把其中一半扔掉了：一章一页的扇形
展开变成了从书里抽出的一张单页，章节改成一条可滚动的数字条——值得记下来，因为这类事情只有
真正做出来才知道，*扇形展开在前几页之后就点不准了，而数字条到九十章依然好用。* 这个阶段
其余的部分就是这类工作必然产生的小修正：间距、对齐、时长、一条配色的取值顺序、一个位置不
对的按钮。

**后端改的每一处，都是界面提出来的。** 整个阶段只加了两处 API，两处都是因为某个界面需要
冻结的契约里没有的东西：TOC 学会了发送每一章的开头正文，因为阅读页应该印出书自己的文字而
不是一段生成的简介；来源学会了完整携带它的原文段落而不是 200 字符的预览，因为
"Full passage" 控件没有东西可打开。这是一条支持在契约冻结*之前*就把界面做出来的论据，而
不是之后。（第三处后端改动来自使用应用，而不是来自界面：带提示的 ASR 解码器在什么都没听
到时，有时会把它自己的词表 prompt 原样交回来，于是应用在回答一个没有人问过的问题。修复的
做法是拿转写结果和 prompt 的开头几个词做比对，然后不带提示重试一次——先试过 token 重叠的
判据，但它把真实问题也判掉了，因为一本短书的词表包含了书里大部分的常用词。）

**11 轮花在一个动效上。** 一本书离开书架、抵达阅读页，最终定在 620ms 的飞行加 150ms 的交
接。11 这个数字很难看，直到你读完每一轮各自修了什么，它才变成一份*可测量地*出错的清单，
而不是一堆口味问题：飞行根本没有动过，因为 StrictMode 的第二次挂载去测目标位置时元素还停
在起始关键帧上，算出来的距离接近零（改成先取消、再测量，飞行随后读到 dx 332px、scale
1.38）；形状在交接那一刻跳变，因为 transform 没法把一根横条变成一张竖立的封面，于是改成让
飞行对封面自己的盒子做动画；偏移量量错了盒子，因为元素是从它自己的左上角开始长大的；返回
的飞行落地时被压扁，因为一本 148px 高的书倾斜 46° 之后静止矩形只有 103px 高；以及书架的退
场被截断在半路，其他书拿到 520ms 滑走，而界面在 110ms 后就被替换掉了。

这些没有一个是测试能够到的。离线套件全程都是绿的，对上面任何一条都没有意见。取代测试的
是*测量*——把计算后的值读回来，而不是相信眼睛。对齐是这样修好的：核对回答卡片和麦克风
都从 x=697 开始，核对章节条和提问框都在 bottom 838 处结束、高度都是 52；两个界面的字标
是靠发现一个 `h1` 的 line-height 是 22.4px、而阅读页的 `span` 继承到的是 24.6px 才对齐
的。"看着还行"从来没有被当成一个结果接受过，这也是早期阶段的自律里唯一完整活到这个阶段
的一条。

这个阶段还产出了对这个应用的使用者最重要的一处订正：**低相关度提示条在好答案上也会
触发。** 它读的是检索置信分数，而在一本真实的书上，这个分数两个方向都会错——"第 2 章
讲了什么"拿到 0.0017，而这个问题是从四条被引用的段落里正确回答出来的；书里从没提过的一
个话题却拿到 0.9953。现在这条警告统计的是：答案自己的句子里有多少条能被事后引用归属追回
到某个段落，并且只在一个实质性答案（>80 字符）一条都没追回时才显示；拒答按设计本来就很
短、也不引用任何东西，所以这个长度判据把它排除在外。分数仍然在计算，仍然随 `sources`
事件一起传出——只是不再决定读者看到的任何东西。这是一处很小的改动，但含义让人不舒服：
这个数字曾作为质量信号发布出去，而它从来没有拿一个已知答案的用例核对过。

## 8. 最终审计：61 个 agent、四个视角，以及一个被要求去反驳的复核者

冻结前的最后一轮是审计而不是评审：**61 个 agent，四个视角**，每一条发现再交给一个独立
复核者，而复核者拿到的要求是*反驳*它。**46 条发现被确认，11 条被驳回**——大约五分之一
没能活过第二次审视，而这正是要做第二次审视的全部理由。一个被要求找问题的 agent，会找出
它预期能找到的那么多问题；反驳这一步就是防止这种胃口变成最终记录。被确认的代码问题在一轮里修完；被确认的文档问题，就是这份文件、TESTING.md、SPEC 的说明和 mock 被订正的
依据。

审计能抓到、而测试和一个人到处点击都抓不到的东西：

- **一条从来没有匹配上的样式选择器。** 五组规则给 `.shelf__help` 写了样式，而按钮渲染出
  来的是 `.shelf-help`。因此这个帮助控件从写下来那天起就缺席了两个界面的转场，它的返回
  动画一次都没跑过——构建看不见，测试看不见，眼睛也看不见，因为没有动画看起来就像一个
  设计决定。
- **一条跨书残留在状态里的引用。** 读者之前被翻到的那个段落在切换书籍之后仍然留着，于是
  打开下一本书时会被翻到另一本书里毫不相干的一章——章节号在不同的书之间没有任何意义。
- **一次在它的界面消失之后才返回的转写。** 一段录音在读者已经离开阅读页之后才回来，它
  照样把问题问了出去，于是在书架上开始播报一个语音答案。
- **一套只用到一半颜色的配色。** 布面的遍历只推进了色相组合、没有推进色调，所以 32 种
  组合出来的布面里只有 16 种被用过，第 17 本书用的是第 1 本的封面。从来没有人往书架上放
  过 17 本书。
- **一条把两个数字写反了的注释。** 代码注释里的置信度数值前后颠倒了——这类缺陷没有任何
  测试能看见，在运行时不产生任何代价，而以后每一个读到它的人都会相信它。

再加上审计真正要做的那件事，做减法：约 130 行属于已经不存在的侧栏、面板和页头的 CSS，
一条重复的进度规则、其中过时的那份反而生效，两个失去引用的设计 token，四个没人用的
导出，一个每帧都在跑、却服务于一个没人设置的回调的播放电平循环，以及一个不配对的花括号
——每次构建都在往一份没人读的日志里报它（浏览器的恢复方式是静默吞掉它后面的那条规则）。

这份清单里的规律值得点明：里面几乎所有东西，都是在那个没有契约可以对照的阶段写下的。
审计是事后顶替契约的东西，代价是 61 个 agent——作为一个项目的收尾方式这说得过去，作为
一个项目的运作方式则很差。

## 如果重来，我会怎么做

- **测契约，而不是测它的各个实现。** 一份共享的 fixture，记录 SSE 帧*以及 REST 载荷*，
  由 Python 服务端和 TypeScript 客户端双方共同断言，本可以抓住那次引用格式不匹配——而且
  它也能抓住下一次，那一次也确实来了：mock 一直在提供 TOC 章节和来源，而真后端在此期间
  已经多长出了两个字段（§5）。同一份规格的两个手写实现总会漂移，而让其中一个去抄另一个，
  只修好已经发生的那次漂移。
- **更早地端到端跑应用，并且在一个脏数据库上跑。** 两个已交付的 bug 都需要一个真实 key
  和已经存在的数据。一套绿色的单元测试说明各个部件能工作；它对软件真正运行的那台机器
  什么都没说。这本该是一道阶段关卡，而不是最后一步。
- **为回退路径的审计留出预算。** 这个代码库里每一处 `except: log and degrade` 都应该回答
  "这条触发时操作者看到了什么？"至少有一处目前的答案是"什么都看不到"，这就是一个坏掉的
  base URL 变成了状态差一点的一天、而不是一个错误的原因。
- **选一本更大的评测用书，或者两本。** 25 页会让每一组的 recall@5 都饱和，包括朴素基线，
  这意味着这套评测框架根本区分不出排名前三的配置。测量是诚实的；仪器太小了，而这是规划
  的失败，不是一个结果。
- **把交互工作放在契约之前，而不是之后。** §7 是 17 轮，属于 §1–§6 的流程没有描述的
  一个阶段，而它的两处 API 改动都来自某个界面发现冻结的契约回答不了它。一份在一周原型
  界面之后才写的规格，规定的会是另一些东西；固定契约买来的并行开发优势是真实的，但这个
  优势有一部分是用 API 后来不得不长出来的字段换的。
- **提前说清楚一个动效将按什么标准判定。** 那 11 轮飞行不是 11 次改主意——每一个修
  的都是一个可证明为错的数值——但流程里没有任何东西事先说明"落位正确"是什么意思，所以
  每个毛病都得先被注意到才能被测量。为一个转场写一份简短的验收清单（从点击的位置开始、
  改变形状而不是缩放、页面保持到落位、可降级为瞬间切换）只花一段文字，就能把其中好几轮
  合并成一轮。
